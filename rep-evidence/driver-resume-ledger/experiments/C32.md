# Experiment: C32 — is adaptive coalescing worth the complexity?

**Pre-registered:** 2026-09-10, iteration 22, before the model was written.

The last live idea in the backlog, carried since iteration 1: *"target a fixed
ledger write rate rather than a fixed window `W`. Harder to reason about,
probably correct."* It has to be settled or buried before the loop can claim
exhaustion.

## The asymmetry that motivates it

With a fixed `W`, two quantities move in opposite directions as the completion
rate `r` changes:

- **write rate** `= r/W` — grows with `r`, and must stay under the durable-write
  ceiling
- **redo time window** `≈ W/r` — grows as `r` *falls*, because a slow phase takes
  longer to accumulate `W` units

So a fixed `W` tuned for the fast phase over-exposes the slow phase in time, and
one tuned for the slow phase overshoots the write ceiling when things speed up.
Adaptive `W = ceil(r / target_rate)` holds the write rate at `target` by
construction, and shrinks `W` when `r` falls — bounding both.

That is the argument. It is also exactly the kind of argument that sounds
airtight and turns out to buy nothing, which is what the control is for.

## Claim

- **C32.** Adaptive coalescing bounds **both** the write rate and the redo time
  window across a varying workload, where any single fixed `W` bounds only one.
  *Refutes if:* adaptive misses the target write rate by >20 % at some completion
  rate, **or** its worst-case redo exceeds that of a fixed `W` achieving the same
  write rate, **or** a single fixed `W` matches adaptive on **every** profile.

The third clause is a negative control written into the claim itself. If a fixed
`W` does just as well everywhere, adaptivity is complexity for nothing and should
be buried rather than specified.

## Profiles

| profile | shape | role |
|---|---|---|
| `constant` | flat rate | **negative control** |
| `step` | 10× rate change mid-job | the motivating case |
| `ramp` | smooth 100× sweep | tests tracking, not just switching |
| `bursty` | alternating fast/slow | tests responsiveness vs hysteresis |

`constant` is the control and it is load-bearing: with no rate variation there is
nothing for adaptivity to exploit, so adaptive **must not** beat fixed `W` there.
If it does, the comparison is rigged — most likely by tuning the fixed `W` badly
— and the whole run is **VOID**.

## Policies compared

1. `fixed_mean` — `W` tuned to the profile's *mean* rate
2. `fixed_peak` — `W` tuned to its *peak* rate (safe on writes, bad on redo time)
3. `adaptive` — `W = clamp(ceil(r_observed / target), 1, W_max)`

All three are measured on identical rate traces, with the ledger write rate
target set to 10 % of the 262/s same-key ceiling (26/s), consistent with C3.

## Prediction (frozen)

1. **`constant`: adaptive ties `fixed_mean`**, within 5 % on both metrics.
   Confidence 0.85. Anything else voids the run.
2. **`step` and `bursty`: adaptive holds write rate within 20 % of target while
   both fixed policies violate one bound** — `fixed_mean` exceeding the write
   ceiling in the fast phase, `fixed_peak` inflating redo time in the slow phase.
   Confidence 0.7.
3. **`ramp`: adaptive tracks**, with max write-rate deviation under 20 %.
   Confidence 0.6 — a 100× sweep is the hardest case and hysteresis may lag.
4. **Adaptive's worst-case redo in *units* is no better than fixed_peak's** and
   may be worse. Confidence 0.6. Stated explicitly because it is the honest cost:
   adaptive optimises redo *time*, not redo *units*, and the design must not
   claim both.

## What each outcome means

| `constant` | varying profiles | reading |
|---|---|---|
| tie | adaptive holds both bounds | **C32 proven.** Specify adaptive `W` in the REP, with the fixed-`W` fallback. |
| tie | fixed `W` matches everywhere | **C32 refuted** — bury the idea, keep fixed `W`. A clean, cheap negative result. |
| adaptive wins | any | **VOID** — the fixed baseline was mistuned. |
