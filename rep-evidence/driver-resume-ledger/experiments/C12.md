# Experiment: C12

**Pre-registered:** 2026-09-10, before the session-scoping harness was written.

## Claim

Scoping ledger keys by `session_name` prevents a new cluster that reuses an
existing `gcs_storage_path` from adopting a stale ledger, given that the KV DB's
cluster-id guard is disabled.

## Why this is not paranoia

`ValidateOrWriteClusterIdMarker` would `RAY_LOG(FATAL)` on a cluster-id
mismatch (`rocksdb_store_client.cc:266-295`), but `InitKVManager` passes
`expected_cluster_id = ""` (`gcs_server.cc:791`) and the check no-ops when the
expected id is empty. The `/tables` client is constructed differently
(`gcs_server.cc:226-231`). So **a brand-new cluster pointed at an existing
`gcs_storage_path` silently inherits every prior `internal_kv` key.** KubeRay's
RayJob retry path recreates the cluster while a PV may well be reused, so this
is a normal operating sequence, not an exotic one.

## Refutes if

`session_name` is not stable across head restarts, or a stale ledger from a
prior cluster can still be adopted despite the scoping.

**The claim has two halves and only one of them is testable here.** The rig can
settle whether scoping prevents adoption. Whether `session_name` is stable
across a head restart is a property of Ray, evidenced by code reading
(`node.py:1607-1630`, which persists it alongside the marker file that solves
the RocksDB bootstrap problem) and only confirmable in stage C. This experiment
therefore settles half a claim, and the card says so up front rather than
letting a green result imply more than it does.

## Setup

- Run a complete job to termination under `session = "session-A"`.
- Without clearing the store — modelling a reused PV — start a coordinator under
  `session = "session-B"`.
- `INV-SESS`: the new session's carry-forward must recover **nothing**.
- Also check the converse: session B must not delete session A's keys, since a
  reused path may hold a ledger someone still wants.

## Prediction (frozen)

1. Scoping works: session B recovers an empty state, and B's sweep leaves every
   session-A key intact. Confidence 0.9 — this is a prefix, and prefixes are not
   subtle.
2. NC9 (`session_scoped=False`) is red on both counts: B adopts A's completed
   ledger *and* B's sweep deletes A's keys. I expect B to recover all N units
   and then execute **zero** — a silently completed job that never ran.
3. The failure mode under NC9 is the dangerous one *because* it looks like
   success: a job that reports done in milliseconds having done nothing.

## Thresholds

- **PASS:** zero `INV-SESS`, and zero session-A keys deleted.
- **FAIL:** either.
- **VOID:** NC9 green.

## Result

- Run id: `runs/20260910-044833-C12`
- Outcome: **uncertain** — half settled, and recorded as `uncertain` rather than
  `proven` precisely because the other half is not.

**Settled by the rig.** On all three workloads, a coordinator started under
`session-B` on a store still holding `session-A`'s completed ledger recovered
**nothing**, re-executed **every** unit, and destroyed **none** of the prior
cluster's keys. Exactly as predicted.

**NC9 red, and its failure mode is the one worth quoting.** Without scoping the
new cluster executed **zero** of N units and deleted the prior cluster's ledger
in the process. A job that reports success in milliseconds having done nothing
at all, while destroying the evidence that it did nothing. That is a far worse
outcome than a crash, and it is the default behaviour if the `session_name`
prefix is left out — which nothing in Ray would stop you doing, because
`InitKVManager` passes `expected_cluster_id = ""` and the cluster-id guard
no-ops.

**Not settled.** Whether `session_name` survives a head restart. Code reading
says yes (`node.py:1607-1630`) but code reading is not evidence of behaviour,
and this is the hinge the whole claim turns on: if `session_name` changed across
a head restart, the scoping would protect against a foreign cluster by hiding
the ledger from the coordinator's own restart — turning a safety measure into a
guaranteed total loss. Split out as **C21**, `blocked` on stage C.
