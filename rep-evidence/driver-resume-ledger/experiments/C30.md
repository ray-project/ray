# Experiment: C30 — is the redo window a constant or an interval?

**Pre-registered:** 2026-09-10, iteration 19, before the repeat rig was written.

C27 predicted `redo = Q·W + 2W` exactly and was refuted by a single point:
`Q=16` gave **53**, not 54. Four of five arms matched exactly. The obvious
reading is "off by one, close enough" — which is precisely the reading this loop
does not accept.

The diagnosis is that the final term is not a constant. At the instant of death
the producer holds `p` units in its `pending` batch, where `p ∈ [1, W]`:

    redo = Q·W  (queue)  +  W  (writer's dequeued batch)  +  p  (producer's partial batch)

Arithmetic for `Q=16`: durable 45 + queue 48 + writer 3 + p = 98 executed ⇒
**p = 2**. The other four arms caught `p = W = 3`.

## Claim

- **C30.** The async redo window is `Q·W + W + p` with `p ∈ [1, W]`, so
  `Q·W + 2W` is a *tight upper bound*, and measured redo **varies** across
  repeats at fixed `Q`.
  *Refutes if:* repeated runs at fixed `Q` all yield an identical redo, **or**
  any measured redo falls outside `[Q·W + W + 1, Q·W + 2W]`.

## Why this is not curve-fitting

The refutation condition is deliberately built on a prediction the generating
observation could not make. C27's data said "one point was 53". C30 says
something stronger and separately checkable: **at a single fixed `Q`, the answer
should not be the same every time.** If six repeats at `Q=8` all return exactly
30, then `p` is effectively always `W`, the interval story is wrong, and `Q=16`'s
53 needs a different explanation entirely.

There is a real reason to doubt C30, and it should be stated before running.
Once the queue is full during an outage, `run()` blocks *inside* `q.put` with a
**complete** batch of `W` in hand — so the steady state during a long outage is
`p = W`, and death should almost always catch it there. `p < W` only occurs in
the brief interval after a successful `put` and before the next block. So the
honest prior is that variation exists but is **rare**, which is why this samples
the crash phase rather than repeating one timing.

## Setup

Six repeats at `Q=8`, `W=3`, identical in every respect except the moment of
death, which is swept across the batch phase:

| repeat | death at (into outage) |
|---|---|
| 1–6 | 25.0, 26.3, 27.6, 28.9, 30.2, 31.5 s |

Sweeping the phase is the *fair* way to sample `p`: the claim is that redo
depends on where in the produce/enqueue cycle the crash lands, so the experiment
must land in different places. Each repeat gets its own cluster, storage path,
job scope and actor name.

Predicted interval at `Q=8`: `[28, 30]`.

## Prediction (frozen)

1. **Every measured redo lies in `[28, 30]`.** Confidence 0.8.
2. **At least two distinct values appear across the six repeats.**
   Confidence 0.5 — genuinely uncertain, for the steady-state reason above.
   This is the clause that decides the claim.
3. **`p = W = 3` is the modal outcome** (redo 30). Confidence 0.7.
4. All repeats contiguous, no duplicates, queue saturated at death.

## Negative control

Every repeat must be confirmed **saturated** (`queued == Q`) at death. An
unsaturated repeat is testing a smaller buffer than labelled and its point is
invalid — this is the failure that starved iteration 16. A run in which fewer
than four repeats saturate cannot settle the claim.

## What each outcome means

| observation | reading |
|---|---|
| all in `[28,30]`, ≥2 distinct | **C30 proven.** The redo window is an interval; `Q·W + 2W` is the design's number because it is the worst case. |
| all exactly 30 | **C30 refuted.** `p` is not varying, and `Q=16`'s 53 has another cause that must be found before any redo bound is trusted. |
| anything outside `[28,30]` | **C30 refuted**, and the accounting is wrong in a way neither C27 nor C30 captured. |
