# Experiment: C15

**Pre-registered:** 2026-09-10.

## Claim

The uniqueness of compaction base keys (`base@n` rather than one `base`
overwritten in place) is load-bearing **only** against a concurrent stale
writer, not against crashes.

Raised in iteration 1, when NC6 — in-place base overwriting — passed 6,513
sequential crash traces, contradicting the design doc's stated crash-safety
justification for unique base keys.

## Refutes if

A single-writer crash interleaving exists in which an in-place base loses
committed progress (would mean iteration 1 missed it), **or** a concurrent
interleaving exists in which `base@n` uniqueness prevents a loss that in-place
would suffer (would mean uniqueness *is* load-bearing, and the doc's conclusion
was right for the wrong reason).

## Setup

NC6 (`compact_in_place=True`) under the **concurrent** driver at 2 and 3
instances, on top of the C17 + C20 read ordering, alongside the unmodified
protocol as the comparison arm.

## Prediction (frozen)

**In-place base overwriting will be clean, and C15 will therefore be *refuted*
in its second clause — uniqueness turns out not to be load-bearing at all,
under crashes *or* concurrency.**

Reasoning, committed before the run: the writer publishes the base *before* the
pointer, so an in-place `base` key is only ever overwritten with a state that is
a **superset** of what it held, because the ledger state is a grow-only set. A
reader that takes the pointer last and the base after it can therefore observe a
base that is *newer* than the pointer suggests, which is harmless, but never one
that is older. The single case that unique keys genuinely protect against —
`base@p` disappearing between the pointer read and the base read — cannot arise
when there is only one base key, because only the sweep deletes it, and the
ascending epoch scan (C20) already handles the sweep.

If that is right, the honest conclusion is that **the design doc recommends
unique base keys for a reason that does not exist**, and the recommendation
should be downgraded to a preference (it makes compaction auditable and makes a
torn read detectable) rather than presented as a safety requirement.

## Thresholds

- **C15 clause 1 confirmed:** in-place clean under sequential crashes (already
  observed in iteration 1; re-run as a regression).
- **C15 clause 2 refuted:** in-place also clean under 2 and 3 concurrent
  instances.
- **C15 proven:** in-place clean sequentially but violating concurrently.
- **VOID:** the comparison arm (unmodified protocol) shows violations, which
  would mean the run is measuring something other than the flag.

## Result

- Run id: `runs/20260910-044833-C12`
- Outcome: **refuted** — in the second clause, as predicted.

In-place base overwriting was **clean** on every arm: 6,585 sequential crash
traces (confirming iteration 1), 630 two-instance traces and 1,110
three-instance traces, with the unmodified comparison arm clean throughout. So
`base@n` uniqueness is not load-bearing against crashes **or** concurrency.

The mechanism is the one committed before the run: the ledger state is a
**grow-only set** and the base is published before the pointer, so an in-place
base is only ever overwritten with a superset of what it held. A reader taking
the pointer last may observe a base *newer* than the pointer implies, which is
harmless; it can never observe an older one. And the single case unique keys
would genuinely protect against — `base@p` vanishing between the pointer read
and the base read — cannot arise when there is only one base key, because only
the sweep deletes it and the C20 ascending scan already covers the sweep.

**Consequence for the design doc:** unique base keys are a *preference*, not a
safety requirement, and the doc's crash-safety justification for them is wrong.
They remain worth keeping for two reasons that are about operability rather than
correctness — compaction becomes auditable, and a torn read becomes detectable
rather than silent — and those are the reasons that should be written down.

**No surprise.** Prediction and outcome matched, including the direction of the
refutation.
