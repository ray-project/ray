# Experiment: C25 — the coordinator's pinning must be soft

**Pre-registered:** 2026-09-10, iteration 13, before the harness was modified.

`runs/20260910-055803-headfail` split cleanly: the ledger survived, the actor
**name** survived, and the epoch survived — but reattach failed with
`ActorUnschedulableError`, because the coordinator was pinned with
`NodeAffinitySchedulingStrategy(node_id=..., soft=False)` to a node id that no
longer existed after the restart.

That is a *placement* bug, not a durability bug, and it is the kind of finding
that is easy to over-read. The single run cannot tell the difference between:

- **(a)** hard pinning is the cause, or
- **(b)** the coordinator was unrecoverable for some other reason and the
  affinity error was merely the first exception raised on the way.

Distinguishing (a) from (b) is the entire point of this experiment, and a single
green `soft=True` run would not do it either — it would only show that *one*
configuration works.

## Claim

- **C25.** A detached coordinator must use soft or no node affinity: hard
  `NodeAffinitySchedulingStrategy(soft=False)` makes it permanently
  unschedulable after the pinned node disappears, even though its name, its
  ledger and its epoch all survive.
  *Refutes if:* a hard-pinned coordinator is successfully rescheduled after its
  node is replaced, **or** a soft-pinned one fails to be.

Note the refutation condition is two-sided on purpose. Both directions must
come out as predicted or the claim is not proven.

## Setup

Three **arms**, each a full independent run: fresh storage path, fresh cluster,
`ray start --head` + one worker, coordinator placed **off-head**, work committed,
`gcs_server` SIGKILLed, head restarted on the same path and port, reattach
attempted from a fresh driver. The three arms differ in exactly one line:

| Arm | Placement of the coordinator |
|---|---|
| `hard` | `NodeAffinitySchedulingStrategy(node_id=<worker>, soft=False)` |
| `soft` | `NodeAffinitySchedulingStrategy(node_id=<worker>, soft=True)` |
| `none` | no scheduling strategy at all — plain `.options(name=..., lifetime="detached")` |

The `hard` arm is the **negative control**. It is a re-run of iteration 12's
configuration and it is *required to fail again*. If `hard` succeeds this time,
the original failure was flaky or environmental, the run is **VOID**, and
nothing may be concluded about `soft` from it either.

The `none` arm exists because `soft=True` and "no strategy" are not the same
thing and only one of them is what the design should actually recommend. If
`none` works, it is the simpler recommendation and the design should say so.

## Prediction (frozen)

1. **`hard` fails to reattach**, with `ActorUnschedulableError` naming the
   missing node. Confidence 0.9. This reproduces iteration 12.
2. **`soft` reattaches successfully**, on whichever node is available after the
   restart — most likely the freshly started head, since the old worker's raylet
   is gone. Confidence 0.75. The residual risk is that the *actor restart* path
   caches the original scheduling decision rather than re-running it, in which
   case `soft` would fail for a different reason and C25 would be refuted in the
   more interesting direction: **no** affinity setting is safe and the
   coordinator would have to be re-created rather than restarted.
3. **`none` reattaches successfully.** Confidence 0.8.
4. In every arm that reattaches, the recovered coordinator reports
   `resumed_from > 0` — it must come back **with** its progress, not as a blank
   incarnation. A reattach that succeeds but resumes from 0 would be a *worse*
   outcome than an unschedulable actor, because it is silent.

## What each outcome means

| `hard` | `soft` | `none` | Reading |
|---|---|---|---|
| fail | ok | ok | **C25 proven.** Design must forbid hard affinity. |
| fail | fail | ok | C25 proven in spirit but sharper: only *no* affinity is safe. New claim for the `soft` failure mode. |
| fail | fail | fail | **C25 refuted in the dangerous direction** — actor restart cannot cross a node replacement at all, and the ledger design's coordinator tier needs a re-create-by-name path rather than relying on `max_restarts`. This would be the loop's fourth refutation and a load-bearing one. |
| ok | * | * | **VOID.** The negative control did not fire; iteration 12's failure was not reproducible. |

## Fidelity gaps carried in

- **F8** (med) still applies: the harness `ray stop --force`s before restarting
  the head, so the worker raylet dies too. For C25 this is *acceptable and even
  necessary* — the claim is precisely about the pinned node disappearing, and
  F8 guarantees it disappears. F8 remains a problem for C4 and C7, not here.
