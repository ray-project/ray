# Experiment: C7 + C4 (duplication clause) — a GCS outage the coordinator survives

**Pre-registered:** 2026-09-10, iteration 14, before the harness was written.

Every cluster-level run so far has restarted the head with `ray stop --force`,
which kills the worker raylet and the coordinator too. That is recorded as gap
**F8**, and it makes two questions unreachable:

- **C7** asks whether a GCS outage degrades to *"work continues, durability
  pauses"*. If the coordinator dies with the head, there is no work to continue
  and nothing to observe.
- **C4**'s refutation condition has three clauses — dead, **duplicated**, or
  name lookup fails. `ray stop --force` guarantees the old coordinator is dead
  before the new head returns, which is exactly the condition under which
  duplication is impossible. The harsher test **destroys the hazard it is meant
  to detect**.

Both need the same thing: an outage that the coordinator *survives*.

## Setup

`ray start --head` (rocksdb storage) + one worker node. Coordinator placed
off-head, **no scheduling strategy** (C25), created with `max_concurrency=3` so
that `info()` can be answered while `run()` is blocked — without that, a wedged
`run()` and a healthy-but-busy one are indistinguishable from outside.

The outage is produced by capturing `/proc/<pid>/cmdline` of `gcs_server`,
`SIGKILL`ing it, and later **re-executing that exact argv**. Nothing else is
stopped. The raylets keep running and reconnect to GCS on their own
(`gcs_rpc_server_reconnect_timeout_s`, default 60 s).

A **sampler** driver is started *before* the kill and polls `info()` every 2 s
into `samples.jsonl`. It must pre-exist, because `ray.init` itself needs GCS and
so a new driver cannot be started during the outage. The sample stream is the
measurement; the final state is only a cross-check.

## Claims

- **C7.** GCS unavailability degrades to "work continues, durability pauses"
  without deadlocking the coordinator or tripping the GCS health check.
  *Refutes if:* the outage deadlocks the coordinator, grows a queue without
  bound, or leaves it wedged after GCS returns.
- **C4 (duplication clause).** No second live incarnation appears when GCS
  reloads the actor table while the original coordinator is still running.
  *Refutes if:* two incarnations are simultaneously live, or the surviving one
  is silently replaced.

## Prediction (frozen)

1. **`executed_this_incarnation` keeps rising during the outage.** Confidence
   0.4 — deliberately low. The coordinator's unit loop calls `commit()` every
   `W` units, and `commit()` is a synchronous `internal_kv` put. If that put
   blocks, work stops *with* durability rather than continuing without it, and
   C7's premise is simply false as written. That is the most likely single
   outcome and it would be a genuine refutation, not a rig defect.
2. **The coordinator does not die.** Confidence 0.8. Its raylet is untouched.
3. **After GCS returns, progress resumes and the ledger is consistent** — no
   gap, no duplicate unit, `epoch` unchanged at 1 (no restart happened).
   Confidence 0.6. The named hazard is **ray#55996**: `DEADLINE_EXCEEDED` is not
   retried by the GCS client and wedges the caller, so a put issued *during* the
   outage may never recover even after GCS is healthy. If progress stays flat
   after restoration, that is ray#55996 reproducing, and it is the single most
   important negative result this loop could produce for the ledger design — it would mean the
   ledger's write path needs its own timeout-and-retry wrapper rather than
   trusting the client.
4. **No duplicate incarnation.** Confidence 0.7. GCS reloads the actor table
   from `tables/` and should recognise the actor as still alive rather than
   recreating it. A duplicate here would be severe: two live coordinators in the
   *same* epoch, which epoch fencing does not prevent, because both hold the
   same instance id.

## Negative controls

- **NC-outage.** The same run with **no kill at all** must show monotonically
  rising progress and a rising ledger write count throughout. If the no-kill arm
  also stalls, the stall is not caused by the outage and the run is **VOID**.
- **NC-sampler.** The sampler must record at least one sample in which the
  `info()` call itself fails or times out *if* the actor is genuinely wedged. A
  sampler that returns identical values without ever erroring cannot distinguish
  "wedged" from "idle", so a flat progress curve with zero sampler errors is
  **inconclusive**, not a refutation.

## What each outcome means

| during outage | after restore | reading |
|---|---|---|
| progress rises | resumes | **C7 proven** — the degradation is what the design assumed |
| progress flat | resumes | C7 refuted as stated, but benignly: the ledger write is on the critical path, so an outage pauses *work*, not just durability. Design must either accept it or make commits asynchronous. |
| progress flat | still flat | **ray#55996 reproduced.** C7 refuted in the dangerous direction; the ledger design needs its own retry wrapper. |
| coordinator dead | — | C4 refuted (dead clause) and F8 was hiding it |
| two live incarnations | — | **C4 refuted on the duplication clause** — the worst outcome available here |

## Fidelity gaps

- Re-executing the captured `gcs_server` argv is not identical to KubeRay
  starting a fresh head pod: the new process inherits the same port, the same
  storage path and the same log directory, and no other head process is
  restarted. It is a *GCS process* failover, not a *pod* failover. New gap if
  the run turns on this distinction.
