# Experiment: C23 — the injected cluster-scope key

**Pre-registered:** 2026-09-10, before the probe or the fix were written.

## Claim

A ledger scope key that distinguishes **cluster restart** from **cluster
replacement** must be injected by the orchestrator (RayCluster `metadata.uid`,
or an equivalent), because no identity Ray can self-derive survives a reused
storage path.

*Refutes if:* an in-cluster identity exists that is **stable across a head
restart** *and* **changes when a new cluster is created against a reused
`gcs_storage_path`**.

This is C12's replacement and, per the final report, the ledger design's single highest open
risk. It is also a **universal negative**, which means it can only ever be
*supported*, never proven — so this experiment does two things: it tries hard to
refute it, and it verifies the proposed fix independently of the outcome.

## Part A — try to refute it

Enumerate every cluster-identity candidate reachable from Python on Ray 2.58 and
measure each across three boots:

1. fresh storage path
2. restart on the **same** path (models a head restart)
3. fresh path again (models a genuinely new cluster)

A candidate refutes C23 only if it is **identical** in (1) vs (2) **and
different** in (1) vs (3). Candidates: `session_name`, the GCS `cluster_id` via
`GcsClient`, `node_id`, the `/tmp/ray` session directory, the GCS address, and
`RAY_CLUSTER_NAME` / autoscaler cluster name if present.

## Part B — verify the fix regardless

Scope the ledger by an **injected** key read from the environment — standing in
for `RayCluster.metadata.uid` via the Kubernetes downward API — and check both
directions, because only checking one is how C12 passed review in the first
place:

- **same injected uid across a restart** → the ledger **is** adopted, and the
  job resumes. (If this fails, the fix has traded a silent-corruption bug for a
  guaranteed-total-loss bug, which is worse.)
- **different injected uid on the same storage path** → the ledger is **not**
  adopted, the new job executes every unit, and it does **not** delete the
  prior ledger.

## Prediction (frozen)

1. **No candidate refutes C23.** Confidence 0.8. `session_name` is already known
   to be path-derived. I expect the GCS `cluster_id` to be path-derived too,
   because the `/tables` client validates it with
   `ValidateOrWriteClusterIdMarker` and a mismatch is `RAY_LOG(FATAL)` — a
   cluster restarting on its own disk must therefore see the same id, which is
   exactly the property that makes it useless here. `node_id` and the GCS
   address should be unstable across restart, failing the *other* half.
2. **The injected key works in both directions**, and is about 5 lines.
3. **A false hope to check explicitly:** the `/tmp/ray` session directory is
   *not* on the PV, so it might look like a discriminator. It will fail because
   it is unstable across a head restart too — the head pod gets a fresh
   `/tmp`. I want that written down before measuring, because it is the kind of
   thing that looks like a fix for ten minutes.

## Thresholds

- **C23 SUPPORTED:** no candidate satisfies both halves, **and** Part B passes
  both directions.
- **C23 REFUTED:** some candidate does. Then C12 is repairable in-cluster and
  the KubeRay dependency disappears — a much better outcome, which is why the
  probe enumerates candidates rather than assuming the answer.
- **VOID:** the probe cannot distinguish (1) from (3) for *any* candidate,
  including ones expected to differ — that would mean the probe is not
  measuring cluster identity at all.

## Result

- Run ids: `runs/20260910-055447-C23a` (Part A) and `runs/20260910-055536-C23b`
  (Part B). Ray 2.58.0.
- Outcome: **C23 proven (as strongly as a universal negative can be) · C24
  proven** — the injected key works in both directions.

### Part A — nothing inside the cluster can do this job

Nine candidates enumerated. **Zero usable.** The table splits perfectly in two:

| candidate | survives head restart | detects replacement |
|---|---|---|
| `session_name`, `session_dir`, `runtime_ctx_cluster_id`, `gcs_client_cluster_id`, `RAY_CLUSTER_NAME`, storage-path marker, storage dir listing | **yes** | **no** |
| `gcs_address`, `node_id` | **no** | no |

And the reason is **structural, not incidental**. A head restart and a cluster
replacement on a reused PV are the *same physical event* from inside the
cluster: a process starting against an existing storage path. No function of
in-cluster state can return different values for one event. The requirement
"stable across a same-path boot **and** different across a same-path boot" is
self-contradictory.

`gcs_client_cluster_id` was the most promising candidate and fails for the most
instructive reason: the `/tables` client validates it with
`ValidateOrWriteClusterIdMarker`, and a mismatch is `RAY_LOG(FATAL)`. It is
*required* to be stable across a restart on its own disk — which is exactly the
property that makes it useless here. It is not an oversight that Ray has no
usable identity; it is a consequence of what identity means on a persistent disk.

### The probe was wrong the first time, and it mattered

The first version compared boot 1 against boot 3 — a **different storage path** —
and duly reported four "usable" candidates including `session_name`, which stage
C had *already measured to be inherited*. It was answering "can you tell two
clusters apart when they have different disks", which is trivially yes and is
not the hazard.

Two runs of the same probe, opposite conclusions, from one wrong comparison.
Corrected before anything was recorded, and noted here because a green result
from the wrong comparison is the single most repeated failure in this loop.

### Part B — the fix, in both directions

| direction | result |
|---|---|
| same uid, same disk (head restart) | claimed epoch 2, **`resumed_from = 10`, executed 0 units** |
| different uid, same disk (recycled PV) | claimed epoch 1 in its own namespace, `resumed_from = 0`, **executed all 10 units** |
| does the foreign cluster damage the original? | **no** — the prior 3-key ledger was left intact |

Both directions matter. A "fix" that failed the first would have traded silent
corruption for guaranteed total loss, which is worse than the bug — and checking
only the second direction is precisely how C12 passed review in the first place.

The key is about five lines, and it has to come from outside: Part A shows there
is nowhere inside to get it.

|---|---|
