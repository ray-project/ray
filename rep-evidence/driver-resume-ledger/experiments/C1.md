# Experiment: C1 (+ new claim C16)

**Pre-registered:** 2026-09-10.

> **Disclosure, because it changes how much this card is worth.** Unlike
> `experiments/C6.md`, this card was **not** written before the rig existed. The
> concurrent driver had to be built first, and building it required running it,
> and running it surfaced violations. Three separate rig defects were found and
> fixed during that bring-up (below), and the third fix immediately exposed a
> failure in the design. The predictions here are therefore **informed by
> bring-up observations** and must not be read as blind. What *is* genuinely
> pre-registered is (a) the classification rules, (b) the thresholds, (c) the
> distinction between what refutes C1 and what refutes the new C16, and (d) the
> proposed fix and the experiment that will test it in iteration 3. Iteration
> 3's card **will** be blind, because the fix has not been implemented yet.

## Claims under test

**C1 (existing, load-bearing).** The M1 epoch protocol — absent-key CAS,
read-back, and epoch-scoped immutable state keys — admits exactly one legitimate
writer per epoch, under lost acks, GCS restart and a partitioned stale
coordinator.

*Refutes if:* two instances read back their own id for the same epoch, or a
stale instance's write is read as current-epoch state.

**C16 (new, load-bearing).** Epoch scoping is *sufficient* to make a fenced
coordinator harmless: a coordinator that keeps running after a higher epoch has
been claimed cannot cause the new epoch to lose committed progress.

*Refutes if:* any interleaving exists in which a unit acked by an instance that
still held the highest claimed epoch is not recoverable after a higher epoch
completes its carry-forward.

C16 exists because C1 is **under-specified**, and the loop found that out the
hard way. C1 protects against a stale writer *corrupting* the new epoch. The
design doc's argument for it is verbatim: *"A stale coordinator that still
believes it holds epoch k physically cannot corrupt epoch k+1's state, because
it does not write those keys."* That statement is true. It is also beside the
point, because the stale coordinator can destroy epoch **k**'s state while
epoch k+1 is in the middle of reading it.

## Setup

- Rig: `python3 poc/run_checker.py --experiment C1 --out runs/<id>`
- New component: `poc/concurrent.py` — two coordinator instances (A, then B)
  interleaved at KV-operation granularity, replayed from a decision list so the
  search can backtrack without cloning a generator.
- Sweep: spawn point for B over every operation index of A; **full interleaving
  enumeration** for a window of `w` scheduling steps after B spawns
  (`w ∈ {4, 6}`); round-robin outside the window; A's stale tail capped at 8
  operations *after it is fenced*.
- Cross-check: seeded random interleaving fuzzer, seeds `[1, 2, 3]`, which
  branches at every step and is not bounded by the window.
- Workloads: `(N, W, K) = (4,1,2)` and `(6,1,2)`.

### The durability contract, stated before looking at results

An ack is **covered** by INV-DUR only if the acking instance still held the
highest claimed epoch at the moment of the ack. That is what a fencing token
*means*: once a higher epoch exists, the old instance's promises are void. Acks
issued after that point are counted separately as `fenced_acks` and reported by
`INV-FENCE-ACK`. Writing this rule down before analysing results matters,
because the alternative rule ("every ack is covered") would refute the design
trivially and unfairly.

### Three rig defects found during bring-up, all of which produced clean results for the wrong reason

1. A's stale tail was budgeted from the moment **B spawned** rather than from
   the moment **A was fenced**. A burned the whole tail before B claimed
   anything, so the interesting window was never entered.
2. `Ack` was treated as conflict-free. It is not: whether an ack is fenced
   depends on reading the epoch keyspace, so it conflicts with epoch-key writes.
3. **The partial-order reduction starved B.** Fixing the order of
   "commuting" operations meant A always ran first and simply finished the job
   before B was ever scheduled. Every trace came back clean because no
   interleaving was ever explored. Replaced with exhaustive enumeration inside a
   bounded window plus round-robin outside it.

Defect 3 is the same failure as iteration 1's control problem wearing different
clothes: **the rig reported success because it was not looking.** That is now
twice, from two unrelated causes, which is a strong argument for keeping a
"could this result have been produced by a rig that does nothing?" check as a
standing item rather than a one-off.

## Prediction (frozen, and informed — see disclosure)

1. **C1 as literally stated survives.** `INV-ONE` never fires: the absent-key
   CAS plus read-back genuinely admits one winner per epoch. Confidence 0.9.
2. **C16 is refuted**, by a torn carry-forward read. Predicted mechanism, in
   full, so that a different mechanism counts as a surprise:
   - A (epoch k) commits and acks units while still holding the top epoch.
   - B claims epoch k+1 and begins reading epoch k: `base_ptr`, then `base@p`,
     then the segment list, then each segment.
   - A, now fenced but still running, compacts epoch k: writes `base@m`, flips
     `base_ptr` to `m`, then **deletes** segments `≤ m`.
   - B's segment reads return `None` for the deleted keys, and B's `base@p` is
     the *pre-compaction* base. B carries forward a state missing every unit
     between `p` and `m`, then sweeps epoch k, destroying the evidence.
3. **`INV-FENCE-ACK` fires in a large fraction of traces** — I predict over half
   — because the commit path has no fence check at all. I classify this as a
   **contract** violation rather than a safety one: the lost work is redone, so
   at-least-once still holds (C10), but the coordinator has told its driver that
   work is committed when the ledger will not return it.
4. `INV-ONE`, `INV-PTR` and `INV-GC` all stay clean.

## Thresholds

- **C1 PASS:** zero `INV-ONE` violations across the full sweep and the fuzz.
- **C1 FAIL:** any `INV-ONE`, or any trace in which a fenced instance's write is
  read as current-epoch state.
- **C16 REFUTED:** ≥ 1 `INV-DUR` violation with a covered ack.
- **C16 PASS:** zero, across both the windowed enumeration and ≥ 1,200 fuzz
  traces over 3 seeds.
- **INCONCLUSIVE** for either: fewer than 500 traces reach a state where a
  fenced instance issues any operation. The rig must be shown to have entered
  the window it is claiming to have searched — this is defect 3's permanent
  countermeasure.

## Negative controls

| control | how it breaks the mechanism | expected |
|---|---|---|
| NC1 `fence_mode=ignore` | never checks the CAS result at all | `INV-ONE` RED |
| NC2 `fence_mode=inverted` | reads `_internal_kv_put`'s inverted return as "I won" | `INV-ONE` RED — and note *which* instance wins |
| NC3 `epoch_scoped_state=False` | one shared state keyspace across epochs | `INV-DUR` RED, and worse than the real protocol |
| **coverage control** | count traces in which a fenced instance executed ≥ 1 operation | must be ≥ 500, else the run is INCONCLUSIVE |

NC1 and NC2 are the two bugs that pass every happy-path test, which is the whole
reason the read-back step exists. If either comes back green, the fencing part
of this run is void.

## The fix this experiment is expected to motivate (pre-registered so iteration 3 is blind)

If C16 is refuted as predicted, the fix is **not** to stop the fenced writer —
that cannot be done reliably over a store with no CAS on values. It is to make
the *reader* immune:

> **Read the segments before the pointer, and retry if the base named by the
> pointer is missing.**

Sketch of why that should work, written before implementing it: a segment `i`
can only be deleted by a compaction at some `m ≥ i`, and that compaction sets
`base_ptr = m` *before* deleting. So a reader that reads segments first and the
pointer second will always observe a pointer `p ≥ m ≥ i` for any segment it
failed to read, and `base@p` contains that segment's units by construction. The
remaining hole — `base@p` itself being deleted by a later compaction between the
pointer read and the base read — is closed by re-reading the pointer and
retrying, bounded, since a fenced writer performs finitely many compactions.

Iteration 3 will implement this, keep the current read order as a new negative
control, and require the control to go red on the very counterexample found
here. That is a genuinely blind test of the fix, and it is the reason this
sketch is being committed now rather than after the run.

## Result (filled in after the run)

- Run id: `runs/20260910-042707-C1` (git `2019059`).
  **The first attempt, `runs/20260910-042522-C1`, is retained as a VOID run** —
  see below. It is evidence and has not been deleted.
- Outcome: **C1 proven · C16 refuted**

### The void run

`runs/20260910-042522-C1` voided itself on its own pre-registered rule: NC2
came back completely **CLEAN**. The card had predicted `INV-ONE`.

The prediction was wrong, and the way it was wrong is the interesting part.
With the inverted return read as "I won", the instance that actually *creates*
the epoch key sees `raw = 1`, computes `won = (raw == 0) = False`, and concludes
it lost. So does the next one, and the next. **Every instance aborts.** No
instance owns an epoch, so `INV-ONE` cannot fire; no instance acks anything, so
`INV-DUR` cannot fire. Total failure was indistinguishable from success.

So the footgun in `internal_kv.py:100` does not cause split brain in a
two-instance system — it causes a **complete, silent livelock**, in which a job
sits at zero progress while its coordinator restarts forever. Arguably worse
operationally, and much harder to attribute.

`INV-LIVE` was added to the concurrent driver and the run repeated. That is the
**third** time in this loop that the rig has reported clean because it lacked an
invariant able to see the failure (iteration 1's controls; the starved
scheduler; this). Treating "could a rig that does nothing have produced this
result?" as a standing checklist item is no longer optional.

### The counterexample

Trimmed from `results.json → real["tiny/w=6"].minimal_inv_dur_log`. A owns
epoch 1 and has acked units 0–3 while still holding the top epoch, so all four
are covered by the durability contract:

```
    A#31: Delete(key='session-A/job1/state/0001/seg/0003')
    B#7: Get(key='session-A/job1/state/0001/seg/0003')
    A#32: Delete(key='session-A/job1/state/0001/seg/0004')
    B#8: Get(key='session-A/job1/state/0001/seg/0004')
    B#9: Put(key='session-A/job1/state/0002/base@0002', value={'seq': 2, 'done': [0, 1]}, overwrite=True)
    B#10: Put(key='session-A/job1/state/0002/base_ptr', value=2, overwrite=True)
    B#12: Delete(key='session-A/job1/state/0001/base@0004')
    B#13: Delete(key='session-A/job1/state/0001/base_ptr')
    B#17: Put(key='session-A/job1/state/0002/seg/0003', value={'seq': 3, 'done': [2]}, overwrite=True)
    B#18: Ack(units=(2,))
    B#20: Put(key='session-A/job1/state/0002/seg/0004', value={'seq': 4, 'done': [3]}, overwrite=True)
    B#21: Ack(units=(3,))
    B#22: Put(key='session-A/job1/state/0002/base@0004', value={'seq': 4, 'done': [0, 1, 2, 3]}, overwrite=True)
    B#23: Put(key='session-A/job1/state/0002/base_ptr', value=4, overwrite=True)
    B#25: Delete(key='session-A/job1/state/0002/base@0002')
    B#26: Delete(key='session-A/job1/state/0002/seg/0003')
    B#27: Delete(key='session-A/job1/state/0002/seg/0004')
    audit#3: Note(text='audit owns epoch 3')
    audit#4: Get(key='session-A/job1/state/0002/base_ptr')
    audit#5: Get(key='session-A/job1/state/0002/base@0004')
    audit#6: Keys(prefix='session-A/job1/state/0002/seg/')
    audit#7: Put(key='session-A/job1/state/0003/base@0004', value={'seq': 4, 'done': [0, 1, 2, 3]}, overwrite=True)
    audit#8: Put(key='session-A/job1/state/0003/base_ptr', value=4, overwrite=True)
    audit#10: Delete(key='session-A/job1/state/0002/base@0004')
    audit#11: Delete(key='session-A/job1/state/0002/base_ptr')
    audit#13: Delete(key='session-A/job1/epoch/0002')
```

Read the interleaving at `B#4` … `B#8`. B reads `base_ptr = 2`, then A flips it
to 4 and starts deleting the segments B is *about to read*. B's `Get` on
`seg/0003` and `seg/0004` return `None`, B carries forward `{0,1}`, and then B
sweeps epoch 1 — deleting `base@0004`, which held all four units. Units 2 and 3
are gone from the ledger and are re-executed at `B#16` and `B#19`.

### Surprise

**The design doc's argument for M1 is true and irrelevant.** It says: *"A stale
coordinator that still believes it holds epoch k physically cannot corrupt epoch
k+1's state, because it does not write those keys."* Every word of that is
correct, and this run confirms it — `INV-ONE` and the stale-write-read-as-current
condition were never violated. But the stale coordinator does not need to write
epoch k+1's keys to destroy the job. It only needs to **delete epoch k's**,
which it does as a matter of routine, because compaction is a delete-heavy
operation and nothing tells a fenced coordinator to stop compacting.

Epoch scoping protects the *writer*. Nothing protected the *reader*.

Second, smaller surprise: **NC3 (state not epoch-scoped) produced fewer `INV-DUR`
violations than the real protocol** — 18 against 28 on the same workload.
Sharing one keyspace means a fenced writer's later writes are at least *visible*
to the new epoch. That does not make NC3 safe; it makes NC3 a poor control for
these invariants, and it is recorded here rather than presented as a pass.

### Envelope

`INV-DUR` violations require the window `w ≥ 6`: at `w = 4` the enumeration
found none, and the fuzzer (unbounded window) found them at roughly ten times
the rate of the windowed search. The bug lives in a specific and slightly deep
interleaving — B must be *between* its pointer read and its segment reads when A
compacts — which is exactly the kind of race that a real cluster would hit rarely,
intermittently, and unreproducibly. Fidelity gap F5 (the window bound) is
therefore **load-bearing for the negative direction**: had this run come back
clean, the window bound would have been the first suspect.
