# Experiment: C17 (the C16 fix, verified)

**Pre-registered:** 2026-09-10, before the fix was implemented. The fix itself
was committed one iteration earlier, in `experiments/C1.md` § *The fix this
experiment is expected to motivate*, before the refutation was even analysed.
**This card is blind.**

## Claim (restated after refutation)

C16 was refuted as originally worded. It is restated, not deleted:

> **C16′.** With the carry-forward read reordered — segments first, `base_ptr`
> last, with a bounded retry when `base@ptr` has vanished — a fenced coordinator
> cannot cause the new epoch to lose committed progress.

## Refutes if

Any interleaving in which a unit acked by an instance that still held the
highest claimed epoch is not recoverable after a higher epoch completes its
carry-forward. Same condition as before: the goalposts have not moved.

## Why this should work (argument committed before the run)

A segment `i` can only be deleted by a compaction at some `m ≥ i`, and that
compaction writes `base@m` and sets `base_ptr = m` **before** it deletes
anything. So for any segment a reader fails to read, the pointer it subsequently
reads is already `≥ m ≥ i`, and `base@p` contains that segment's units by
construction. Reading the pointer *last* converts "I might have missed a
segment" into "anything I missed is already in the base".

The residual hole is `base@p` itself being deleted by a *later* compaction
between the pointer read and the base read. That is closed by re-reading the
pointer and retrying, bounded at 4 attempts, since a fenced writer performs
finitely many compactions before it dies.

## Setup

- Rig: `python3 poc/run_checker.py --experiment C16 --out runs/<id>`
- Same concurrent driver, same workloads `(4,1,2)` and `(6,1,2)`, same spawn
  sweep, windows `w ∈ {4, 6, 8}` — **8 is new**, deliberately deeper than the
  window at which the refutation appeared, since a fix that only works inside
  the window that found the bug is not a fix.
- Fuzz cross-check: seeds `[1, 2, 3, 4, 5]` (up from 3), 500 traces each.

## Prediction (frozen)

1. **Zero `INV-DUR` violations**, at every window including `w = 8`. Confidence
   0.75. The argument above is a proof sketch, not a proof, and the loop has
   already caught me being confident about M1.
2. **`INV-FENCE-ACK` is unchanged**, still firing in over half of traces —
   roughly 10,000. The fix protects the *reader*; it does nothing about a fenced
   coordinator telling its driver that work is committed. That is a separate
   defect and gets its own claim rather than being smuggled into this fix.
3. **Redo does not vanish.** Units committed by A but acked after it was fenced
   are still re-executed by B. The fix bounds the loss to the *fenced* window;
   it does not eliminate redo, and if the numbers show redo dropping to zero I
   should suspect the rig, not celebrate.
4. `INV-ONE`, `INV-PTR`, `INV-GC`, `INV-LIVE` all stay clean.
5. The C6 sequential sweep, re-run unchanged, stays clean — the reordering must
   not have broken single-writer crash-safety.

## Thresholds

- **PASS:** zero `INV-DUR` across all windows and all 2,500 fuzz traces, **and**
  NC13 red, **and** the C6 regression clean, **and** coverage ≥ 500.
- **FAIL:** any `INV-DUR`.
- **VOID:** NC13 green, or coverage below 500.

## Result (filled in after the run)

- Run id: `runs/20260910-043110-C16`
- Outcome: **proven**

### Observed vs predicted — every prediction held

| prediction | outcome |
|---|---|
| (1) zero `INV-DUR` at every window including `w = 8` | **held.** 0 across 51,144 windowed-exhaustive traces and 5,000 fuzz traces over 5 seeds |
| (2) `INV-FENCE-ACK` unchanged, roughly 10,000 | **held**, and then some — 38,826 of 51,144 |
| (3) redo does not vanish | held; fenced work is still redone by the new epoch |
| (4) `INV-ONE` / `INV-PTR` / `INV-GC` / `INV-LIVE` clean | **held**, all zero |
| (5) the C6 sequential sweep still clean | **held**, 7,620 traces clean |
| NC13 (the pre-fix order) red on `INV-DUR` | **held** — 28 violations on the same workload that produced 28 in `runs/20260910-042707-C1` |

Coverage: **49,393** traces reached a live fenced instance, against a floor of
500. The `w = 8` sweep is deeper than the `w = 6` at which the refutation first
appeared, so this is not a fix that only works inside the window that found the
bug.

### Surprise

**NC1 (`fence_mode=ignore`) lost its `INV-DUR` violations.** In
`runs/20260910-042707-C1` it produced 126 `INV-ONE` *and* 206 `INV-DUR`; here it
produces 126 `INV-ONE` and **zero** `INV-DUR`.

That was not predicted, and it is a genuinely useful result. It says the
reader-side fix protects the carry-forward read even when fencing has failed
completely and two instances are writing the same epoch concurrently. The fix is
not merely sufficient for the fenced-writer case it was designed for — it
strictly dominates the old order, and it degrades gracefully under a stronger
failure than the one it was aimed at. Mechanically: reading the pointer last
means *any* concurrent compactor, legitimate or not, has already published a
base covering whatever the reader missed.

I am recording that as an observation, not as a claim that fencing is now
optional. `INV-ONE` still fires under NC1, and two instances scheduling the same
work is a different disaster from two instances losing each other's records.

### Envelope

Holds across windows 4, 6 and 8; two workload shapes; unbounded-window fuzzing
at 5 seeds. Untested beyond two concurrent instances, and beyond a stale tail of
8 operations (fidelity gap F6) — a three-instance pile-up, which the
`RESTARTING`-at-GCS-death window could in principle produce, is C13's business.
