# Experiment: C21 — stage C on real Ray

> This is the same experiment as [`C8.md`](C8.md); it is duplicated under C21
> because one run settled four claims and the ledger indexes cards by claim id.

**Pre-registered:** 2026-09-10, before the stage-C rig was written.

Environment: **Ray 2.58.0**, single node, in-process
`ray.init(_system_config={"gcs_storage": "rocksdb", "gcs_storage_path": ...})`.
Confirmed reachable during bring-up; the RocksDB backend accepts this
configuration and creates `kv/`, `tables/` and — **`session_name`** — under the
storage path.

## Claims under test

- **C8.** The reference implementation needs zero Ray core patches on 2.57+.
- **C4a.** A detached, named coordinator survives *driver death* and is
  reattachable by name from a new driver. (C4's head-pod-replacement half needs
  KubeRay and stays out of scope — registered as a gap, not quietly claimed.)
- **C21.** `session_name` is stable across a head restart.
- **C12 recheck.** Scoping by `session_name` prevents a new cluster on a reused
  `gcs_storage_path` from adopting a stale ledger.

## The hypothesis that makes this worth running

Bring-up showed `session_name` is persisted as a file **inside the storage
path**, alongside the RocksDB directories. The design doc already noted this
file exists to solve the RocksDB bootstrap problem (`node.py:1607-1630`). If a
new cluster started against a reused path **reads that file and adopts the old
session name**, then:

- **C21 is proven** — the name survives, because it is on disk, not in memory.
- **C12 is *refuted*** — and refuted *by the same mechanism*. Session scoping
  cannot distinguish "my own cluster restarting" from "a different cluster on a
  recycled PV", because in both cases the session name comes from the same file
  on the same disk. The prefix that was supposed to be a cluster identity is a
  **storage-path identity**.

That would be an unusually clean result: one fact settling two claims in
opposite directions, and killing a mitigation the design doc treats as
sufficient.

## Prediction (frozen)

1. **`_internal_kv_put` returns `True` when the key already existed** —
   confirmed statically in `ray/experimental/internal_kv.py` on 2.58, whose
   docstring reads *"Returns: Whether the value already exists."* Re-confirmed
   dynamically here. Note the path: the design doc cites
   `_private/internal_kv.py`; on 2.58 it is `experimental/`.
2. **A new cluster on the same `gcs_storage_path` inherits the previous
   `session_name`.** Confidence 0.7. → C21 proven, **C12 refuted**.
3. **C8 holds**: the whole design implements on stock Ray with no patch. The
   only wobble is whether `_internal_kv_list` gives usable prefix scans.
4. **C4a holds**: a detached named actor survives its creating driver's exit and
   `ray.get_actor` from a fresh driver returns a working handle.
5. **End-to-end resume works**: kill the coordinator mid-job, and the restarted
   incarnation re-executes at most `W` units.

## Thresholds

- **C8 PROVEN** if every test passes with an unmodified `pip install ray`.
- **C4a PROVEN** if a fresh driver reattaches and observes progress made before
  the first driver exited.
- **C12 REFUTED** if the new cluster inherits the session name *and* the scoped
  ledger is therefore visible to it.
- **C21 PROVEN** if the session name is stable across restart on the same path.
- **VOID** if the RocksDB backend silently falls back to `memory`, in which case
  nothing here is testing durability at all — checked by confirming that a key
  written before the restart is readable after it.

## Result

- Run id: `runs/20260910-045910-stageC` (Ray 2.58.0, single node, in-process,
  `gcs_storage=rocksdb`). An earlier attempt, `runs/20260910-045817-stageC`, is
  **retained**: its C21/C12 findings are identical and valid, but T2/T3 were
  inconclusive because the child driver could not reach the cluster
  (`address='auto'` does not resolve for an in-process `ray.init`). Fixed by
  passing the GCS address explicitly. The run is kept because deleting an
  inconvenient run is exactly what the guardrail forbids.

### Every prediction held, including the one that kills a mitigation

| prediction | outcome |
|---|---|
| (1) `_internal_kv_put` returns True when the key already existed | **confirmed dynamically.** `put(absent) = False`, `put(present) = True`, and the CAS held — the value stayed `a` |
| (2) a new cluster on the same path inherits `session_name` | **confirmed.** Old and new session names byte-identical across a full shutdown/init cycle |
| (3) C8: no core patches | **confirmed.** Everything runs on a stock `pip install ray` |
| (4) C4a: detached actor survives its driver | **confirmed, and better than asked** |
| (5) end-to-end resume with ≤ W redo | **confirmed with *zero* redo** |

### C4a, on real Ray

A subprocess driver created the coordinator with `lifetime="detached"`,
`max_restarts=-1`, fired `run.remote()` and called `os._exit(0)`. The
coordinator then executed **all 40 units with no driver attached at all**, and a
fresh driver in a different process reattached with `ray.get_actor("coord-A")`
and read the progress back.

Then `ray.kill(handle, no_restart=False)`. The restarted incarnation came up in
a new PID, **claimed epoch 2**, reported `resumed_from = 40`, and executed
**zero** further units. Final ledger: **3 keys**, matching stage B's steady-state
prediction exactly.

That is the entire thesis of the design, working, on unmodified Ray.

### C12 is refuted, by the same fact that proves C21

`session_name` is written to a file **inside** `gcs_storage_path`. A cluster
started against that path adopts it. So:

- **C21 proven** — the name is stable because it is on disk rather than in
  memory.
- **C12 refuted** — a *new* cluster on a *reused* path inherits the same name,
  and the prior ledger is therefore sitting under exactly the prefix the new
  cluster is about to use. Measured directly:
  `prior_ledger_visible_to_new_cluster = True`.

**Session scoping is a storage-path identity, not a cluster identity.** It
cannot distinguish "my cluster restarted" from "a different cluster on my old
PV" — which is the only case it was introduced to defend against. The design
doc's mitigation for the disabled cluster-id guard does not work.

### Surprise

The direction was predicted; the *elegance* was not. One fact — where Ray puts a
small text file — settles two claims in opposite directions and removes a
mitigation. And it is not fixable from inside: **both cases look identical from
within the cluster.** Same disk, same session name, same keys. The distinction
only exists outside, where KubeRay knows whether it created a new RayCluster.
Raised as **C23**: the scope key has to be *injected*, not self-derived.

### Not tested, and not claimed

- **Head pod replacement** (C4's other half). Needs KubeRay; single-node
  `ray.init` cannot reproduce it. C4 stays `uncertain`.
- **GCS p99 for other components under ledger load** (C3's other half). The rig
  is single-node and in-process.
