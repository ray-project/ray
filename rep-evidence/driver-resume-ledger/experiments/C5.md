# Experiment: C5 — is coordinator state actually reconstructible?

**Pre-registered:** 2026-09-10, iteration 15, before the rig was written.

C5 claims coordinator state is fully reconstructible from **two sources** —
the ledger (recorded *intent*) and live-cluster introspection (observed
*reality*) — with no external storage. Everything measured so far has used a
coordinator whose only state is a set of completed unit ids, which is a
degenerate case: it lives entirely in source one. The interesting state is the
kind that exists in the *cluster*: long-lived child actors the coordinator owns.

## The hazard

Creating a child and recording it are two operations, so a crash can land
between them, in either order:

- **record → crash → create.** The ledger claims a child that does not exist.
  Benign: reality is authoritative for existence, and the new incarnation simply
  creates it.
- **create → crash → record.** A child exists that the ledger has never heard
  of. This is the dangerous one. If the new incarnation cannot find it, the actor
  is an **orphan**: alive, consuming resources, owned by nobody, and invisible —
  and the incarnation will create a second one alongside it.

The second case is what decides C5. Note that `lifetime="detached"` children are
*required* for the question to be interesting at all: a non-detached child is
owned by the coordinator's worker and dies with it, so there is nothing to
reconcile and nothing to leak.

## The variable under test: how children are named

- **`opaque`** — child name is a fresh `uuid4`. The ledger entry is the *only*
  link between the job and its children.
- **`prefixed`** — child name is deterministic and scoped:
  `ledger/<scope>/<job>/child-<i>`. The name itself carries the attribution.

This is the crux, and it is **not** about randomness. Named actors are all
listable via `ray.util.list_named_actors`, so even `uuid4`-named children are
*discoverable*. What `opaque` lacks is **attribution**: the new incarnation can
see a name and cannot tell whether it belongs to this job, to another job, or to
an unrelated component. Discoverability without attribution is not
reconstruction.

## Arms

| arm | naming | reconcile step | role |
|---|---|---|---|
| `opaque` | `uuid4` | on | tests whether the ledger alone suffices |
| `prefixed` | scoped, deterministic | on | tests the design's proposed answer |
| `prefixed_noreconcile` | scoped, deterministic | **off** | **negative control** |

Each arm: a phase-1 driver creates `K` children, records only the first `R < K`
into the ledger, then `os._exit(1)` — a crash landing exactly in the
create → crash → record window, `K-R` times over. A phase-2 driver then recovers
and reports.

`prefixed_noreconcile` is the control. Deterministic naming is useless on its own
if nobody looks; the arm must **leak and duplicate**. If it does not, then
something other than the reconciliation logic is cleaning up, the rig is not
measuring what it claims, and the run is **VOID**.

## Prediction (frozen)

1. **`opaque` orphans `K-R` children.** Confidence 0.85. Phase 2 knows about `R`
   of them, adopts those, and creates replacements for the rest, so total live
   children `= K + (K-R)`. Refutes C5 *for opaque naming*.
2. **`prefixed` orphans none.** Confidence 0.7. Phase 2 lists named actors,
   filters by the job prefix, finds all `K`, adopts them, and creates nothing.
   Live children `= K`, duplicates `= 0`.
3. **`prefixed_noreconcile` leaks.** Confidence 0.9 — required, it is the control.
4. **Adopted children answer.** A "recovered" handle that cannot be called is not
   recovery. Every adopted child must return its own identity, and it must be the
   **same pid** as before the crash — proving adoption of the original actor
   rather than silent recreation.

## What each outcome means

| `opaque` | `prefixed` | reading |
|---|---|---|
| orphans | clean | **C5 proven, conditionally** — and the condition is a real design requirement: child names must be deterministic and scope-prefixed, so reality is self-describing without the ledger. |
| orphans | orphans | **C5 refuted.** Some state is genuinely unreachable from either source and the ledger design needs an external index — which contradicts "no external storage". |
| clean | clean | Suspicious: attribution would not be load-bearing. Check whether the rig actually crashed in the window before believing it. |
| — | control clean | **VOID.** |

## Fidelity gaps carried in

- Children here are inert placeholders; a real child holds its own progress. That
  only makes reconstruction *harder*, so a clean result here is an upper bound on
  what a realistic child would give.
- Single-node cluster. C5 is about naming and lookup, which are GCS-level and not
  placement-dependent, so this is adequate.

## Amendment (after the void run, before the re-run)

`runs/20260910-064907-C5children` was **void**: the `prefixed_noreconcile`
control was green when it had to be red. Phase 2 recreated the missing children
with `get_if_exists=True` and the same deterministic names, so Ray returned the
**existing** actors — identical pids — and the "leak" was a bookkeeping artifact
of the rig rather than an observation about the cluster.

Two things follow.

**1. The control was in the wrong arm.** The `opaque` arm is the real negative
control and it *did* fire: four genuinely orphaned children beside four
genuinely new duplicates, with four distinct pids. Attribution is the variable;
"reconciling or not" was never cleanly separable, because deterministic naming
plus `get_if_exists` reconciles implicitly.

**2. There is a simpler mechanism than the one predicted.** Explicit listing was
assumed to be necessary. It is not: `get_if_exists=True` over a deterministic,
scope-prefixed name performs the same reconciliation in one call. That deserves
its own arm rather than being inferred.

Also worth recording, because it bounds the whole failure mode: **Ray requires
detached actors to be named.** The truly unattributable case — a detached child
with no name at all — cannot be constructed. Every leaked child is therefore at
least *discoverable*; what `opaque` naming loses is only the ability to tell
whose it is.

### Revised arms

| arm | naming | recovery path | role |
|---|---|---|---|
| `opaque` | `uuid4` | ledger only | **negative control** — must orphan `K-R` and create `K-R` real duplicates |
| `prefixed_explicit` | scoped | list named actors, filter by prefix, `get_actor`; creates with `get_if_exists=False` | the design's proposed answer |
| `prefixed_getifexists` | scoped | no listing at all; `get_if_exists=True` | the simpler candidate |

`get_if_exists` is now **false** in every creation path except the arm whose
hypothesis it is — precisely so it can never again paper over a failed
reconciliation.

### Added prediction

5. **`prefixed_getifexists` re-acquires all `K-R` unrecorded children with
   unchanged pids and orphans none**, without any listing pass. Confidence 0.85,
   since the void run already showed exactly this by accident. If it holds, the
   design's reconciliation requirement collapses to *"name children
   deterministically from job scope + index"*, and the listing pass becomes an
   audit tool rather than a correctness mechanism.
